Capabilities

What the skill helps you deliver

One skill connects the technical acquisition of Genesys Cloud data with the discipline needed to interpret it.

Reporting and analysis

Investigate queues, agents and IVR flows. Compare matched periods, explain KPI movement and identify the next evidence to collect.

API engineering

Select aggregates, details, observations or jobs. Build scoped payloads and preserve the grain needed for correct results.

Authentication and access

Choose the OAuth grant and regional hosts. Diagnose token, permission, division and user-context failures.

Reliable extraction

Handle cursors, availability watermarks, retries, DST and incremental updates. Reconcile a representative slice with the portal.

Designed for these roles

Reporting analysts, contact-centre consultants, integration developers and technical leads who need reproducible Genesys Cloud evidence.

Scope and boundaries

The skill covers Genesys Cloud. Engage and PureConnect implementation require their own product guidance. Architect, routing, OAuth-client and role changes need an explicitly requested implementation scope.

How it works

From a question to reproducible evidence

  1. Define the question. Resolve selected entities, media, reporting dates, timezone and the desired output.
  2. Establish access. Confirm region, grant type, permissions, divisions and a secure runtime credential binding.
  3. Choose the dataset. Use aggregates for KPIs, details for reconstruction, observations for current conditions and historical user data for availability.
  4. Collect completely. Preserve requests and timestamps. Finish pagination, inspect watermarks and record gaps.
  5. Interpret correctly. Pool sums and counts, compare compatible windows and distinguish observations from hypotheses.
  6. Validate and deliver. Reconcile a scoped slice and report definitions, coverage, findings and remaining limitations.
Success has several stages.

An accepted request, a completed job, fully fetched results and reconciled evidence are different guarantees.

Using the skill

Start with the reporting decision you need

Invoke $genesys-reporting and state the question, selected entities, date window and output. Automatic discovery can also select it for relevant Genesys Cloud reporting work.

Performance investigation

Use $genesys-reporting to compare the Support and Billing queues for the last two complete weeks. Separate voice and messaging, show daily and 30-minute slices, and explain which intervals drive the service-level change. Discover the reporting timezone first.

Authentication diagnosis

Use $genesys-reporting to diagnose a 403 from the conversation aggregate API. We use client credentials. Explain the region, permissions, divisions and grant-compatibility checks without asking for secrets.

Pipeline design

Use $genesys-reporting to design a conversation-detail extraction for these selected queue IDs. Include asynchronous jobs, cursor checkpoints, availability watermarks, late-arriving updates and an upsert strategy.

Reconciliation

Use $genesys-reporting to explain why a portal export and API AHT differ for the same queue-day. Check scope, timezone, event timing, units, sufficient statistics and completeness before changing formulas.

Inputs that improve the result

Provide entity names or IDs, media, date intent, known timezone, the approved connection and desired format. The skill resolves accessible context before asking for information. Never paste client secrets or bearer tokens.

What to expect

API tasks return a precise endpoint, payload or SDK model, access prerequisites and extraction strategy. Reporting tasks return dates, filters, KPI definitions, coverage, findings and material gaps. Authentication tasks identify the failed layer and the narrow remedy.

Authentication

Authentication, identity and access

Select region and identity

Confirm the organization region from its known sign-in URL, connected configuration or administrator-provided region. Select the matching official SDK region host before constructing the API client. Login and API hosts must belong to that environment. Never infer region from user geography, or reporting timezone from region. Example commercial hosts login.mypurecloud.com and api.mypurecloud.com are US East examples, not global defaults. Check current mappings for newer regions and sovereign environments.

Choose client credentials for a service acting as itself; choose authorization code with PKCE for a user-facing application acting with user context. Public clients cannot keep a client secret. Preserve the organization's approved SSO/delegated flow when one exists. Do not design new integrations around legacy implicit grants. Confirm currently supported grant configuration and token behavior from the OAuth client documentation.

Client credentials obtain application authority from assigned roles and divisions, with no human user context. An endpoint requiring a logged-in user can reject that grant even when permissions look sufficient. Do not use /users/me as a universal authentication probe. Test a narrow read appropriate to the actual reporting task.

OAuth wire contract

For client credentials, POST to the confirmed regional login host at /oauth/token over HTTPS. Send Content-Type: application/x-www-form-urlencoded, HTTP Basic authentication using client ID and secret, and body grant_type=client_credentials. Basic encoding is not encryption. Read access_token, token_type and expires_in; retain the token only in the protected runtime and renew shortly before expiration. Client credentials acquire a new token with the same grant, rather than assuming a refresh token.

Platform API requests use Authorization: Bearer <runtime-token> and JSON payloads where the endpoint expects JSON. Do not send a JSON object in place of the token endpoint's form body. Do not send client secrets to an API resource endpoint or place tokens in URLs.

For authorization code/PKCE, validate state, bind verifier/challenge correctly, use the exact registered redirect URI, and exchange the code at the correct regional token endpoint. Consult the current grant guide for refresh and revocation support. Never automate password entry as a replacement for OAuth.

Official Python SDK pattern

Illustrative setup, not executed during skill creation. Dependency: an approved, pinned PureCloudPlatformClientV2 version. The named environment variables are runtime bindings; their values must not be printed.

python
import os
import PureCloudPlatformClientV2 as gc

# Example only: replace with the confirmed organization region.
region = gc.PureCloudRegionHosts.us_east_1
gc.configuration.host = region.get_api_host()
client = gc.api_client.ApiClient().get_client_credentials_token(
    os.environ["GENESYS_CLOUD_CLIENT_ID"],
    os.environ["GENESYS_CLOUD_CLIENT_SECRET"],
)
analytics = gc.AnalyticsApi(client)
# Build the endpoint's typed query model before calling it.
# Keep HTTP debugging disabled where headers/bodies could contain secrets or PII.

Pass the authenticated client to each API class. Do not construct a second unauthenticated client accidentally. Review SDK serialization and automatic token/retry behavior for the installed version before adding duplicate renewal/retry logic. Do not assume a raw dictionary is accepted by a typed SDK method; populate its documented model or use an explicitly supported REST client.

Permission model

Authentication proves identity; access also depends on grant compatibility, endpoint permissions, applicable scopes, role/division grants, licensing and data visibility. OAuth scopes and platform role permissions are different controls. Do not invent scope names from permission names or solve a 403 by assigning blanket administrator access.

Starting permission examples, to verify against the selected endpoint:

NeedTypical platform permission
Conversation aggregatesanalytics:conversationAggregate:view
Conversation detailsanalytics:conversationDetail:view
Flow aggregatesanalytics:flowAggregate:view
User aggregatesanalytics:userAggregate:view
User detailsanalytics:userDetail:view
Queue metadatarouting:queue:view
Architect flow metadataarchitect:flow:view

Some endpoints offer alternative permissions with different visibility, such as agent-specific conversation details. Inspect the endpoint's ANY/ALL requirements. Portal views can need additional permissions beyond the API query. Match the requested divisions; a successful response can still omit inaccessible entities.

For authorized OAuth setup, define the grant, region, minimum roles/divisions, redirect URIs and runtime secret destination concretely before creation. Grant role/division changes through the approved administrator process. Do not embed an organization's client ID, secret or token in this reusable skill.

Diagnose the failed layer

  • Token 400/401: verify form encoding, client type, client authentication, region and configured grant. Avoid logging the request's Authorization header.
  • API 401: check expiry, bearer format, region and which client actually made the call. Reacquire once when justified; stop repeated failures.
  • API 403: check exact permissions, divisions, scope, grant/user-context compatibility and any configured IP restrictions. A different token does not fix missing grants.
  • Empty data: confirm entity IDs, interval, filters and division visibility before concluding there is no activity.

Official references: OAuth client setup, client credentials guide, SDK authentication and regions, SDK token implementation.

Queue aggregate example

Illustrative REST body: QUEUE_ID must be replaced with an explicitly resolved selection. The dates and America/New_York are examples. This window crosses the fall DST change and spans 49 elapsed hours. Confirm metric support and filter schema before execution.

json
{
  "interval": "2026-10-31T04:00:00Z/2026-11-02T05:00:00Z",
  "timeZone": "America/New_York",
  "granularity": "P1D",
  "groupBy": ["queueId", "mediaType"],
  "metrics": ["nOffered", "tAnswered", "tAbandon", "tHandle", "tWait", "oServiceLevel"],
  "filter": {
    "type": "and",
    "clauses": [
      {
        "type": "or",
        "predicates": [
          {"type": "dimension", "dimension": "queueId", "operator": "matches", "value": "QUEUE_ID"}
        ]
      },
      {
        "type": "or",
        "predicates": [
          {"type": "dimension", "dimension": "mediaType", "operator": "matches", "value": "voice"}
        ]
      }
    ]
  }
}

For more queues add predicates to the queue OR clause, retaining the AND relationship with media. A single OR across queue and media would unintentionally broaden scope. Change granularity to PT30M for a separate intraday dataset; do not add that dataset to the daily one. Keep queueId and mediaType in the group so interpretation preserves their populations.

Other diagnostic metrics can include tShortAbandon, tTalkComplete, tHeldComplete, tAcw, nTransferred. Verify support rather than treating this as an exhaustive catalogue. See metrics.md.

Conversation detail example

Details use their own filter model, not aggregate filter, groupBy or granularity fields. A queue filter selects conversations with matching segments; it does not mean all returned participants/segments belong to that queue.

json
{
  "interval": "2026-11-02T05:00:00Z/2026-11-03T05:00:00Z",
  "order": "asc",
  "orderBy": "conversationStart",
  "paging": {"pageSize": 100, "pageNumber": 1},
  "segmentFilters": [
    {
      "type": "and",
      "predicates": [
        {"type": "dimension", "dimension": "queueId", "operator": "matches", "value": "QUEUE_ID"},
        {"type": "dimension", "dimension": "mediaType", "operator": "matches", "value": "voice"}
      ]
    }
  ]
}

This is a synchronous example. Check interval-selection semantics, page/deep-pagination limits and open-conversation behavior. Use the documented asynchronous request model for a bulk job; do not blindly pass paging from this example to a job request.

Preserve the nested grain: conversation → participants → sessions → segments, plus session metrics and flow/outcome fields where present. Queue attribution often lives at segment level. Flattening multiple child arrays together can multiply rows and counts. Apply queue, media, event-time and segment logic to the chosen grain before deriving measures. Do not assume the matching conversation's start date equals the date each metric was emitted.

Metrics

Calculate and interpret metrics correctly

Grain, units and pooling

Retain metric name, group dimensions, interval, statistics and configuration provenance. Raw analytics duration statistics are generally milliseconds; verify the source and convert once. Portal exports may already be seconds or formatted durations. A metric omitted from a sparse response is not automatically zero.

For disjoint compatible slices, pool additive numerators and denominators first. Do not average averages or percentages. Rows missing required sufficient statistics cannot silently drop out of a pooled measure. A zero denominator is N/A, not 0%. Never sum daily and intraday results, base data and drilldowns, or overlapping partitions.

MeasureWorking definition
OfferednOffered.count; queue offers, not distinct callers
AnsweredtAnswered.count; do not replace with connected or handled
AbandonedtAbandon.count, with channel-specific semantics
HandledtHandle.count; its event timing and population differ from answered
ASA in secondssum of tAnswered.sum / sum of tAnswered.count / 1000
AHT in secondssum of tHandle.sum / sum of tHandle.count / 1000
Average wait/abandonown duration sum / own count / 1000
Talk/hold/ACW averagesown tTalkComplete, tHeldComplete, tAcw sum / own count / 1000
Short abandonstShortAbandon.count; obtain the configured threshold
TransfersnTransferred.count; declare a denominator for any rate
Service leveloServiceLevel; preserve returned sufficient statistics and configuration
Flow execution volumeverified nFlow.count; not unique customers
Average flow durationtFlow.sum / tFlow.count / 1000

Worked weighting: one bucket has 10 handles totaling 100 seconds; another has 90 totaling 1,800 seconds. Pooled AHT is 1,900/100 = 19 seconds, rather than the unweighted 15 seconds. A ratio-only export cannot recover an exact pooled rate without its denominator.

Talk, hold and ACW metrics may have different observation populations and boundaries; their averages need not sum to AHT. Counts from event metrics often use stats.count; do not assume sum is an event count or that a metric prefix is a full semantic specification. Preserve actual response statistics.

Service level

Use the API's service-level metric and returned numerator/denominator when available. Confirm response shape and scale before calculating or displaying percentages. Pool sufficient statistics only when threshold and inclusion settings are comparable. If only ratios are available, report the scope-specific ratios or mark pooling unavailable.

Service-level configuration can include/exclude abandons, short abandons and flow-outs, with channel/callback-specific options. Read the relevant organization/queue configuration and reporting-view definition. If unavailable, disclose it; do not substitute a universal formula. Configuration changes can invalidate historical comparisons, and today's setting does not establish last month's setting.

Source for configuration dependence: Queues Activity Detail view. This documentation changes as callback behavior evolves; recheck before implementing callback SL.

Attribution and channel differences

A conversation can traverse several queues, agents, media legs and flows. Adding queue offers measures workload, not deduplicated people or journeys. Answered, offered and handled events can fall in different buckets. Short-interval answered/offered ratios are event ratios rather than same-cohort conversion probabilities; a ratio above 100% can reflect timing rather than a bug.

Callbacks must be separated from voice legs. Customer-first and agent-first lifecycles can attribute events differently. Offered/answered/SL alone do not establish reach, bridge success or customer waiting experience; inspect the relevant lifecycle details. Web messaging, email and asynchronous channels do not inherit voice abandon and duration assumptions. Open/reopened interactions and concurrency affect interpretation.

Define both numerator and population before transfer rate, repeat-contact rate, first-contact resolution, containment, deflection or self-service success. Linked repeat contact needs an explicit identity rule and follow-up horizon. A disconnect is not proof of successful containment; a flow outcome is evidence of its instrumented definition, not an assumed business result. Multiple outcomes per execution are not mutually exclusive.

Agent and workforce reporting

Presence, routing status, on-queue time, utilization, handling work, schedules, adherence and paid staffing are different concepts. Current presence or queue membership cannot establish historical staffing. Use historical user state/detail or the appropriate workforce dataset for the interval, including state definitions, effective membership and reporting eligibility.

Before computing occupancy/utilization, state the exact numerator and eligible-time denominator, media treatment and concurrency model. Adding overlapping digital handle durations can exceed wall-clock time. Do not divide queue handle time by an assumed headcount or treat offered volume as agent productivity. Queue-level SL cannot establish an individual agent's performance.

Trend reasoning

Separate demand, effective capacity, workload, mix, routing and measurement changes. Compare the same local hours, operating calendar, media and definitions. Show absolute volume changes and rate changes in percentage points. Percentage change needs a nonzero baseline. Segment mix can worsen an overall KPI even when each segment improves.

A few days support descriptive findings, not established seasonality or causality. Do not invent targets, confidence intervals or significance from incomplete observations. Distinguish low volume, no returned rows, confirmed zero, unavailable metrics and permission-filtered data.

Definition references: performance columns, reporting FAQs, Flow Outcomes Summary.

Extraction

Retrieve complete, reproducible datasets

Time contract

Record the reporting IANA timezone and its provenance separately from API region and extraction timestamp. Inspect the relevant performance-view setting when available. An offset such as UTC-5 is insufficient to identify a DST-aware region. If sources conflict, resolve the ambiguity with the user; do not guess from computer location.

Resolve relative language into explicit local dates and state the interpretation. For “since last Monday” use an established user convention; absent one, state an interpretation before calculating. The existing investigation convention is the most recent Monday strictly before today, including seven days earlier when today is Monday.

Convert local calendar boundaries with timezone-aware code, using half-open windows [start,end). Freeze one as-of instant for the run and label the current date partial. A local day can be 23 or 25 hours; add calendar dates in the local timezone instead of assuming a fixed 24-hour UTC duration. Retain offset-aware timestamps for repeated fall-back hours. Use the aggregate query's supported timeZone; detail queries use explicit absolute bounds and their own model. Timestamp/alternate-time-dimension choices must match across comparisons.

For local wall times that can be ambiguous or nonexistent, require an explicit offset/fold rule or choose validated calendar boundaries. Python zoneinfo requires installed IANA timezone data; a Windows runtime may require the tzdata package. Do not silently fall back to the machine timezone.

Compare partial days only with equivalent elapsed windows or exclude them from headline deltas. Daily and intraday reconciliation must cover the same instants. Avoid assuming UTC days match the portal's local dates.

Collection manifest

Keep per-run metadata next to immutable raw responses and request bodies. Include only fields relevant to the run:

  • Organization alias/region and connector or SDK version; no secrets.
  • Entity IDs/names/divisions, media/direction, timezone and timezone source.
  • Exact UTC interval and local labels, as-of time, granularity and timestamp convention.
  • Metric names/units, configuration provenance and comparison scope.
  • Requests, job IDs, cursors/checkpoints, response status and correlation IDs when available.
  • Availability watermark, rows/pages retrieved, known gaps, exclusions and completion status.

Use explicit states such as planned, submitted, completed, fully fetched and reconciled. They represent different guarantees. Keep sensitive response bodies out of public reports and exception logs.

Paging and asynchronous jobs

Directory pagination, synchronous detail paging and asynchronous result cursors are different contracts. Verify the endpoint's termination conditions and limits. Do not use an aggregate response limit as if it were a page cursor. A successful capped query may require splitting scope or time to obtain all groups.

For an asynchronous detail extraction:

  1. Check /api/v2/analytics/conversations/details/jobs/availability and document what the current response says is available. A finished computation does not guarantee the most recent interactions were available to it.
  2. Submit the documented async query model; persist the job ID and request metadata without secrets.
  3. Poll that existing job with bounded backoff until a documented terminal state. Respect deadline, failure and expiration states; do not create replacement jobs simply because polling timed out.
  4. Fetch every result page using the returned cursor. Detect repeated cursors and preserve the last durable checkpoint.
  5. Verify fetch completion, scope and coverage before publishing. Record any interval beyond the available watermark as provisional or deferred.

If job submission times out before an ID returns, the outcome is uncertain. Reconcile using connector/job-discovery capabilities when available. Otherwise disclose uncertainty and avoid unbounded duplicate submissions. A correlation ID is useful for support, not proof the request is safely idempotent.

Do not hardcode one lookback, retention window, maximum interval, job lifetime, page limit or rate limit for every API family. Verify current documentation and applicable organization settings. Data absent outside a retention window is not zero activity.

Retries and query size

Start conservatively, for example with two concurrent analytics queries; increase only with evidence that the tenant and endpoint permit it. Honor Retry-After on 429s, supporting either a delay or HTTP date when returned. Use bounded exponential backoff with jitter for transient network/5xx failures; three retries is a useful starting budget, not a platform guarantee. Coordinate with SDK retry behavior.

Do not retry invalid-schema 400s or permission 403s unchanged. For 401, renew once when expiry is the reason. Reduce interval, dimensions or selected-entity batch on query-size errors. Preserve successful partitions and explicit gaps. Split at nonoverlapping absolute bounds with consistent metric semantics; deduplicate overlapping detail results where the API's interval selection returns the same conversation more than once.

Incremental data and storage

Use a watermark based on verified data availability rather than just wall-clock now. Advance the durable checkpoint after all pages and storage commits succeed. Re-query a documented overlap to capture late-arriving metrics and updated conversations, then upsert at the actual grain. A conversation can change after it first appears; append-only conversationStart extraction can miss updates or completions.

Choose stable keys supported by the payload. Conversation ID is suitable for a current conversation snapshot; it is not a unique key for participants, sessions, segments or metric events. Segments may require a documented composite key or snapshot replacement. Preserve raw JSON and schema/version provenance so transformations can be corrected. Do not invent a segment ID that the payload does not provide.

Keep queue, user, flow and division mappings separately, preserving historical versions when needed. Current directory labels and current membership cannot retrospectively reconstruct historical state. Confirm retention, access and approved destination for the user's requested pipeline; do not upload raw tenant data to a new service implicitly.

Reconcile against the portal

Select one queue-day-media slice and match IDs, timezone, dates, media/direction, filters, service-level configuration, timestamp convention and as-of timing. Record the portal view and export units. Compare primitive counts and duration sums before derived averages or rates.

Investigate differences in order: scope/filters → local/UTC boundaries and DST → metric definitions and event timing → permissions/divisions → pagination/caps → delayed data/open interactions → rounding/export transformation. Do not force equality by changing a formula without evidence. Daily and intraday totals should reconcile only where the metric is additive and the populations, coverage and semantics match.

Portal fallback is valid when APIs are inaccessible. Preserve export provenance and map columns explicitly. Missing denominators, sums or numerator counts remain unavailable; do not backfill invented sufficient statistics from rounded averages.

Investigations

Turn evidence into useful findings

Evidence-driven investigation

Start with the user's selected queues, flows, agents or explicit organization scope. Preserve those IDs throughout comparisons. Queue-only, flow-only and combined investigations are valid; never require queue IDs for flow-only work. Freeze extraction time and compare like local windows.

Obtain daily and intraday aggregates for the same population. Keep baseline, media, flow-version, outcome and other drilldowns as separate datasets. Identify the intervals and segments driving a change before collecting narrow details. Check missing buckets, open conversations, provisional data and permission coverage before interpreting trends.

PatternPlausible hypothesisEvidence needed / competing explanation
Volume and delay riseDemand pressureMatched hours and staffing; handle workload may also rise
Volume stable, delay worsensCapacity or routing eligibilityHistorical state, schedules, eligibility; arrivals may have shifted within buckets
AHT grows mainly in ACWWorkflow or case-mix changeWrap-up/contact mix and process history
One queue rises while another fallsRouting or transfer changeLinked journeys and configuration history; independent demand is possible
Flow disconnects riseTechnical failure or self-service changeOutcome, exit, version and error evidence; disconnect alone proves neither
Outcome success declines after releaseRegression or audience changeMatched version/intent populations and unchanged instrumentation

Each material finding should distinguish the observed fact, interpretation, confidence, alternatives and next test. Link to exact local evidence or supplied source identifiers. “Associated with” is appropriate for correlation. State cause only when the evidence supports that stronger claim. Do not collect broad conversation/customer data when a smaller slice can test the hypothesis.

Deliver the format requested

A concise answer may be sufficient. For a file/report, include explicit date range, timezone, as-of time, selected entities/media, coverage, KPI definitions, comparison windows, findings and material gaps. Preserve reusable raw/request evidence locally without embedding it all in the report.

For an offline HTML report: embed required CSS/JS, avoid CDNs/fonts/beacons, and exclude credentials, ANI, transcripts and unnecessary user/customer identifiers. Escape inserted strings and use safe JSON embedding for labels that could contain markup. Show empty/unavailable/provisional states distinctly. Verify it in a supported browser, including filtering and responsive layout. Do not claim visual QA if it was not opened.

For CSV/spreadsheet outputs: preserve numeric duration units and time offsets, identify row grain, distinguish blank from zero, and neutralize formula-like untrusted labels in cells. For a pipeline deliver the actual requested implementation plus checkpoint, paging and late-data strategy; a suggested architecture alone does not complete an implementation request.

  • Flow-only request: uses flow metrics and selected flow IDs, without substituting queue activity.
  • Restricted division: a 200 with missing entities is a coverage limitation until visibility is verified.
  • Timed-out job poll: resume the existing job; do not resubmit it blindly.
  • Ratio-only export: exact pooled service level remains unavailable.
  • Authenticated app with no human context: do not use a user-only endpoint as the token validity test.

For live work, reconcile a small representative slice before broad extraction. Local JSON/schema checks establish structure, not permission, completeness or live metric semantics.

Skill contract

The instructions behind the workflow

Turn reporting questions into correctly scoped, reproducible evidence. Cover both how to retrieve data and what it can establish. Support API design and troubleshooting without requiring a live tenant. A request to create or explain this skill does not initiate tenant access.

Choose the relevant guidance

Read only the references needed:

  • Authentication and access: region selection, OAuth grants, SDK setup, roles, scopes, divisions and secret handling.
  • API selection and requests: aggregate/detail/observation selection, entity discovery, filter placement and request examples.
  • Metrics and interpretation: weighted calculations, attribution, channels, service level, agent state and IVR outcomes.
  • Extraction and reconciliation: timezones, pagination, asynchronous jobs, data availability, retries, incremental loads and portal reconciliation.
  • Investigations and deliverables: comparison design, evidence, reporting outputs and troubleshooting.
  • Source register: official documentation and verification limits; consult when implementing or changing technical contracts.

Working contract

  1. Establish the reporting question, Genesys product, selected entities, media, interval, reporting timezone and desired output. Resolve names to IDs and divisions. Reuse supplied scope; ask only for missing decisions that affect correctness. An explicit organization-wide report is valid; an omitted filter is not authorization for one.
  2. Prefer available authorized connectors. Discover their actual schemas and versions; do not assume a tool named in a prior example exists. Use official SDK/Platform API or mapped portal exports when appropriate. Do not install a third-party server simply to run a report.
  3. Establish the region independently from the reporting timezone. For tenant reporting, inspect the relevant performance-view timezone through an authorized connector or supported UI before asking. Record its provenance; it is not necessarily a universal tenant timezone. For an API-design example use an explicit illustrative timezone, labelled as such.
  4. Choose the smallest dataset that answers the question. Start with aggregates for KPIs, details for conversation-level reconstruction, observations for current conditions, and user state/history for agent availability. Queue aggregates alone cannot establish staffing, occupancy or root cause.
  5. Verify current endpoint method, schema, permissions, allowed dimensions/metrics, limits and preview status in official sources before live implementation. Distinguish REST camelCase from SDK snake_case and typed models. A string field in an SDK is not proof a particular metric is supported.
  6. Preserve request bodies, filter and configuration provenance, extraction time and completeness. Distinguish API success, full retrieval and reconciled results. Follow extraction.md before treating results as complete.
  7. Use sufficient statistics to pool results. Missing is not zero, a zero denominator is N/A, and average-of-averages is usually wrong. Keep observations separate from hypotheses and show material limitations beside findings.

Authorization and data boundaries

A reporting request authorizes relevant reads and documented analytics query/job POSTs. It does not authorize routing, queue, Architect, OAuth-client, role, retention or schedule changes. Prepare any requested setup instructions or code locally; perform tenant changes only within the user's granted scope. Explain that a reporting job POST creates computation, even though it does not change routing configuration.

Use an existing authenticated connection or user-provided runtime secret binding. Never extract tokens from browser storage, credential stores or session histories. Do not request secrets in chat. Keep tokens and client secrets out of source, evidence, debug output and generated reports. Retrieve recordings, transcripts and customer identifiers only when necessary and authorized. Keep raw evidence local or in the explicitly approved destination; do not introduce external uploads or delegated processing implicitly.

For reports, include explicit dates/timezone, as-of time, filters, metric definitions, coverage, findings and material gaps.
