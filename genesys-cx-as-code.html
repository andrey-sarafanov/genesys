Using the skill

When to use it and what to provide

Use $genesys-cx-as-code when you want a Genesys customer journey implemented as versioned code: IVR, voicebots, Web Messaging, SMS or WhatsApp.

The skill turns requirements or an existing export into Terraform resources, Architect YAML, channel wiring and acceptance scenarios. It continues beyond scaffolding to the behavior you requested.

Useful inputs

  • Channels, entry numbers or addresses, target organization and region, divisions and queue destinations.
  • Existing Terraform, lockfile, flow exports and an approved backend/state arrangement.
  • Menus or intents, languages, slots, business API contracts, hours, handoff and error paths.
  • Requested bot engine, environment and the extent of deployment authorization.

Example requests

Use $genesys-cx-as-code to build an English/French support IVR with billing and technical-support choices, holiday routing, bounded retries and agent handoff. Start from this exported inboundCall flow and prepare the development deployment.

Use $genesys-cx-as-code to add Web Messaging with the existing digital bot, an approved domain list and queue fallback. Include the published configuration version, deployment snippet and browser acceptance scenarios.

Use $genesys-cx-as-code to prepare SMS and WhatsApp versions of this journey. Reuse the business contract, adapt presentation and session rules, and identify any provider coverage gaps.

Choose the correct companion

Use Genesys Reporting for Analytics API and data engineering work. Use Performance Investigator to assess queue and IVR results. Neither reporting task requires a flow configuration change.

Helpers

Scaffold, implement and validate

Create a local project

text
python <skill-dir>/scripts/scaffold.py --output <new-directory> --name support --channels ivr voicebot webmessaging sms whatsapp

The helper creates local files, makes no network calls and never applies Terraform. It refuses a nonempty output directory. Run it with an actual skill path; the command is a template, not a deployed application.

Preserve implementation choices

  • --provider-version selects a verified provider baseline.
  • --seed-dir supplies replacement seed files.
  • --substitution KEY=VALUE supplies explicit flow substitutions.
  • --bot-engine CHANNEL=ENGINE preserves native, digital, external or none where supported for that channel.

An external-engine seed records work still needed for the runtime/connector. A menu seed is not evidence of a trained intent/slot bot. Implement the business actions, error paths and useful handoff before declaring completion.

Validate a local project

text
python <skill-dir>/scripts/validate_project.py <project-directory>
python <skill-dir>/scripts/validate_project.py <project-directory> --terraform <terraform-executable>
python <skill-dir>/scripts/validate_project.py <project-directory> --readiness

The checker requires PyYAML. Terraform checks require prior initialization with the intended pinned provider and -backend=false. The helper checks structure and optional Terraform schema/formatting; it never applies infrastructure. Readiness checks recorded implementation, setup and scenario evidence. It cannot independently prove the evidence is true.

What the package supplies

The installed assets include IVR, inbound voice, native bot, digital bot and messaging seeds, plus their accompanying license notices. Reuse the correct seed for the requested engine/channel and preserve notices in generated projects. Seeds require adaptation; their existence does not establish runtime readiness.

What a complete delivery contains

  • Implemented flow YAML, Terraform and necessary runtime code.
  • Channel entry-point wiring and resolved dependency/substitution references.
  • Environment inputs, backend/state decisions and a destination-specific plan when deployment is in scope.
  • Scenario results for every requested channel and concrete pending setup items.
  • Prior code/version and routing references sufficient to execute the proposed rollback.

Foundation

Terraform, identity, dependencies and state

The tested baseline is provider MyPureCloud/genesyscloud 1.87.0. Preserve an existing version unless an upgrade is needed. Pin a verified version and commit .terraform.lock.hcl. The official introduction's old illustrative pins are not current recommendations. Introduction, releases.

Authenticate with a Client Credentials OAuth client having the relevant roles/division access. Supply GENESYSCLOUD_OAUTHCLIENT_ID, GENESYSCLOUD_OAUTHCLIENT_SECRET, and GENESYSCLOUD_REGION through the environment/secret store. Before deployment, compare a verified read-only organization-identity result to the intended target. Do not print credentials.

In 1.87.0, flow filepath points to YAML, substitutions is a string map, file_content_hash is computed, and update_trigger_hash can express extra update dependencies. Old examples assigning file_content_hash fail with this schema. A name change can create a new flow ID while the old flow persists. force_unlock can first publish another editor's draft; create_stubs creates missing dependencies. Pinned flow schema.

YAML names alone do not establish Terraform dependencies. Use substitutions backed by resource/data-source outputs, or a justified depends_on. Parameterize destination divisions and names. Resolve destination IDs rather than carrying source-org GUIDs across organizations.

Export narrowly in a separate directory with genesyscloud_tf_export: filters, dependency resolution, HCL output, data-source replacement, and optional state export are available. Select the modern Architect exporter for YAML. Inspect permission warnings and unresolved references. Exported state belongs to its source org; flow version numbers may change on import. Exports do not preserve every secret, history, or function binary. Retain a function's source/deployment artifact separately. Pinned export guide.

Use distinct backend/state identities and credentials for development and production, preferably separate roots sharing modules. Local state is a learning convenience; team use needs suitable locking storage. Backend reconfiguration is different from state migration: do not silently migrate dev state into production. Generate a destination-specific plan after identity/backend checks, inspect publication/activation/replacements/removals, and apply only to the authorized target. A Git revert does not undo messages, purchases, external transactions, or new GUIDs.

IVR and voicebots

Implement the telephony journey

Use inboundCall menus for DTMF and tasks for business logic. Bind E.164 numbers, hours/holiday flows, and schedules with genesyscloud_architect_ivr. Flow creation and number routing are separate resources; telephony availability is another prerequisite. Pinned IVR schema.

Implement requested choices, repeat/return paths, bounded retries, prompts/languages, hours, data-action failures, and useful agent handoff attributes. The bundled IVR seed only exits a menu; replace it with the requested behavior. For a voicebot, call a supported native or selected external bot action and handle its returned intent/slots, failures, and escalation.

Native voicebots use botFlow. The bundled intent seed adapts an official Genesys blueprint and collects intent before exiting; implement the requested business action and handoff in the bot or caller. Recognition followed by disconnection is not a completed service bot. Official bot blueprint, Call Bot Flow.

Author representative utterances, entities, slots, validation/confirmation, and return values. Configure voice endpointing, barge-in, no-input timing, and reprompts. Use current schemas or exports rather than digital-menu fields. Test silence, noise, interruption, ambiguity, invalid/corrected slots, explicit agent requests, backend timeouts, and transfers over the actual telephony path.

Web Messaging

Wire the browser entry point

Use inboundShortMessage with the chosen bot and fallback/handoff. Web Messaging is assigned through Messenger deployment; legacy inbound chat has a different flow type. Get started, call a digital bot.

Create/reference genesyscloud_webdeployments_configuration and genesyscloud_webdeployments_deployment. Bind configuration ID, its published version, and flow_id. Configure languages, launcher, domain allowlist, session behavior, and appearance. Use the generated snippet, not a guessed region CDN URL. Keep deployment inactive until activation belongs to the release. Pinned configuration, deployment.

Add the snippet to the requested website/test page; use supported Messenger SDK operations for custom behavior. Never embed provider OAuth credentials in browser code. Use a supported auth integration for verified identity; contact attributes alone do not authenticate customers.

Test domain restrictions, reload/resume, language selection, attachments, replies, bot escalation, queue handoff, and agent replies. Keep plain-text alternatives for bots shared with SMS. Architect's bot test does not prove website/deployment routing.

SMS

Adapt the journey for text messaging

Use a provisioned number or supported BYO SMS integration, Message Routing, and an inboundShortMessage flow with a supported bot/queue. Messenger deployment is for Web Messaging. Message Routing, SMS overview.

genesyscloud_routing_sms_address represents a postal address, not an SMS number or a flow binding. Check pinned provider coverage for numbers and route attachment. If absent, implement a verified API/SDK operation or documented admin action, retaining address/flow IDs, prior mapping, and readback. Do not invent genesyscloud_routing_message_route. Postal-address schema, attach route.

Design for plain text, typos, numeric/keyword choices, delayed replies, duplicates, threading, and short messages. Adapt digital quick-reply sample menus to supported SMS input rather than assuming buttons exist. For outbound requests, choose the verified agentless API or messaging campaign as appropriate; implement applicable sender, opt-in/opt-out rules and designated test recipients. Recheck current regional/channel requirements.

Test Unicode/segmentation, STOP, delayed replies, delivery failure, duplicates, fallback, and agent replies. Add a custom backend only for runtime needs native flows cannot meet; use server-side secrets, verified webhook authentication, and idempotency for business side effects.

WhatsApp

Connect business messaging safely

Reference an existing business integration or use authorized Genesys Embedded Signup, then attach its address to inboundShortMessage through Message Routing. Meta onboarding/number verification is separate from bot YAML. Keep interactive account-owner steps with the authorized owner. Embedded Signup, ACD setup.

Provider 1.87.0 exposes genesyscloud_conversations_messaging_integrations_whatsapp: creation requires name and embedded_signup_access_token; optional activate_whatsapp holds phone_number and pin. The resource does not attach an inbound message route. Use its data source for an existing integration instead of recreating it to build a bot. Treat tokens/PINs as secrets; sensitive variables hide presentation but not state storage. Pinned schema.

Use native/digital/external bots with channel-supported messages and text fallback. Recheck current service-window, opt-in, and template requirements for proactive/out-of-window messages. Do not assume Messenger widgets or unrestricted free-form outbound text work here. Template use, template setup.

Test inbound routing, media/menus, languages, template/parameter matching, expired-window handling, errors, escalation, and agent replies with an authorized test account. Deliver pending Meta approvals as concrete setup steps, not a claimed completed deployment.

Bots and APIs

Implement intent, slots and business actions

For each intent, implement utterances, slots, validation, confirmation, business action, outcome, handoff attributes, and failure handling. A digital menu satisfies a menu request; it does not constitute a trained conversational intent bot. Keep return contracts consistent with the calling flow.

For a conversational prototype with no engine specified, the bundled native intent/slot seed can serve voice, Web Messaging, SMS, and WhatsApp through Call Bot Flow; use the corresponding native engine options. The digital seed demonstrates a menu. A selected Digital Bot Flow that needs intent/slot collection requires authoring those actions against its current schema or export; do not copy voice-specific fields into a digital flow or present the menu as equivalent.

Native botFlow and digitalBot settings/actions differ. Use current Architect/Archy schemas or a fresh export. Implement no-input/no-match, correction, retries, exit, escalation, and timeout behavior. Transfer in the bot where supported or in the caller; inspect actual failure/exit outputs before wiring them. Archy schemas, substitutions.

Use supported integrations/data actions for business APIs. Define request/response contracts and timeouts. Mock locally; test auth, bad responses, missing records, permission failures, rate limits, and retries in development. Do not retry non-idempotent operations without an idempotency key or verified outcome. Pinned data actions.

For a selected external engine, version/deploy its bot or runtime separately from the Genesys connector, and map its intent/entity/session/escalation contract. Connector provisioning does not train the third-party bot. Verify transport/signatures. Supported message actions.

For requested generative behavior, use the chosen runtime, permitted knowledge, business-tool boundaries, fallbacks, and evaluation conversations. Keep Codex authoring separate from runtime. A generated statement cannot prove a business action succeeded.

Reuse business/intent contracts across channels, while keeping speech, presentation, rich-content limits, session timing, and outbound constraints specific to each channel. Test each independently.

Verification

Verify the journey and prepare a release

The helper checks manifest/YAML structure; it does not implement the entire Architect grammar. With initialized Terraform, it adds formatting/schema validation against the pinned provider. Test any runtime service with appropriate application tests too.

For stronger offline YAML validation, use current Archy JSON schemas/editor tooling. Confirm commands with archy --help and per-command help; do not assume archy validate exists or that archy create is read-only. Commands, schema refresh.

Check substitutions, startup/cross-flow references, resource lookups, unexplained source-org GUIDs, and requested behavior. Capture licensing/integration dependencies. Before an authorized development apply, verify org/region, permissions/divisions, and backend. Inspect the plan; flow apply publishes and may immediately change routed traffic. Read back IDs, versions/status, dependencies, and channel mappings; inspect Architect.

Exercise every channel: success, handoff, no-input/no-match, invalid input, hours where applicable, backend failure, and channel-specific cases. Record actual results, environment, and evidence such as redacted transcripts/conversation IDs/readbacks. Do not record unperformed tests as passed.

--readiness checks for missing implementation/setup/scenario evidence but cannot judge whether that evidence is true. Use it after real tests, not as independent runtime certification.

For production, build a destination-specific plan and retain prior code/YAML, state/version references, and route mappings. Rollback restores/re-publishes a known-good flow and mappings, followed by entry-point tests. Reverting Git alone does not recover GUIDs or reverse external side effects. Publication behavior.

Skill contract

The full skill instructions

Turn the requested journey into working Architect YAML, Terraform configuration, channel wiring, and acceptance scenarios. Continue through implementation and available validation. A scaffold or a description of a flow is not a completed build.

Select the implementation

Use Terraform for supported resources, Architect YAML for conversation logic, and application code only for required runtime services. The current provider publishes YAML through Architect jobs APIs; a separate Archy CLI installation is optional for authoring, exports, and schema tooling.

RequestYAML flow rootsChannel wiring

VoicebotbotFlow called by inboundCallNative or selected external engine, speech behavior, ACD fallback
Web messaginginboundShortMessage, usually digitalBotMessenger configuration/version, deployment, website snippet
SMSinboundShortMessage, supported botProvisioned number, Message Routing; outbound API/campaign if requested
WhatsAppinboundShortMessage, supported botWhatsApp integration, Message Routing, approved templates when required

Read foundation.md for a new project, migration, or provider upgrade. Load only relevant channel references: voice.md, webmessaging.md, sms.md, whatsapp.md. For bots/backend calls, also read bots.md. Use verification.md before delivery or deployment; sources.md identifies authoritative sources.

Establish the journey and target

Inspect repository instructions, lockfile, YAML exports, backend/state configuration, and supplied requirements. Identify entry points, languages, intents/menu choices, slots, API calls, hours, handoff, no-input/no-match behavior, and acceptance criteria. Keep unrelated tenant resources outside the build.

Use existing flow exports as the strongest starting point. Without exports, adapt the bundled seeds and consult current Architect schema/action documentation. Do not convert digitalBot into botFlow by renaming its root. Ask for missing information only when it materially changes design or prevents a required next step; continue independent implementation.

Preserve the requested bot engine. Codex authors the application; it is not automatically the runtime bot. Do not introduce OpenAI, Lex, Dialogflow, or another hosted service merely because the user asks to vibecode.

Implement locally

The standard-library helper creates a new project with provider configuration, flow resources, entry wiring, a journey manifest, and scenario files:

text
python scripts/scaffold.py --output <new-directory> --name support --channels ivr voicebot webmessaging sms whatsapp

Run from this skill directory or use absolute script paths. --seed-dir supplies replacements matching the generated manifest filenames; --provider-version changes the tested baseline. --bot-engine whatsapp=native (or digital, external, none on messaging channels) preserves a chosen engine; voicebot supports native/external. External mode creates an entry seed and records the connector/runtime work to implement, rather than silently replacing the engine. It refuses a nonempty destination, performs no network calls, and never applies Terraform. Its manifest starts with implementation_complete: false; complete the requested journey before changing that status.

The seeds demonstrate minimal menus/intent recognition and handoff. Implement the user's business logic, slots, messages, failures, and channel adaptations. Complete every requested channel. If the pinned provider lacks SMS/WhatsApp route attachment, implement a verified API/SDK operation or the documented admin action; missing Terraform coverage does not remove that channel from scope.

Consult the pinned provider docs and terraform providers schema -json before adding resources/fields. Use current API Explorer for operations outside provider coverage. Record versions used; the research baseline is not a permanent latest-version claim. Bind substitutions to Terraform resources/data sources or environment inputs, making ordering explicit. Create dependencies before calling flows and channel entry points. Use data sources for deliberately unmanaged resources; import only when taking management is requested.

For a missing provider operation, build a small helper from the verified request schema. Include target lookup, current-state comparison, bounded asynchronous-job polling, and readback. Reconcile uncertain outcomes before retrying mutations. Do not invent endpoints, payloads, commands, or resources.

Validate and deliver

text
python scripts/validate_project.py <project-directory>
python scripts/validate_project.py <project-directory> --terraform <terraform-executable>

Use the available Python interpreter; on Codex desktop, load_workspace_dependencies can locate a bundled interpreter when Python is absent from PATH. The local checker requires PyYAML (python -m pip install PyYAML for that interpreter if absent). It checks required flow files, YAML shape, startup references, duplicate reference IDs, substitutions, channels, and scenarios. The second command adds Terraform formatting/schema checks after terraform init -backend=false. Neither authenticates to Genesys or proves live conversation behavior. --readiness rejects missing implementation/setup/test evidence; it does not independently prove the evidence is true.

For an authorized development deployment, publish in the named org, inspect the flows in Architect, exercise each channel, and record outcomes. Parser and Terraform checks cannot certify Architect expressions, NLU training, permissions, integrations, or live routing. Finish the locally buildable application even when credentials/onboarding prevent connected tests, and identify exact pending connected steps without claiming they succeeded.

Deliver implemented files, a journey diagram when useful, environment inputs, commands, scoped test results, remaining setup, and rollback instructions. Distinguish local validation, development-org validation, and production readiness.

Deployment boundaries

A skill/local build does not authorize flow publication, phone purchases, account onboarding, campaigns, or messages. Respect prior authorization for a named environment without asking again. When an external action is not authorized, first finish the reviewable implementation/plan, then request that specific authorization.

Applying genesyscloud_flow publishes. An update can immediately change a routed customer journey; a saved Terraform plan applies without another Terraform prompt. Check org, region, and backend before an authorized apply. Protect secrets, state, and plan files; keep OAuth secrets and WhatsApp tokens out of source/logs. Leave force_unlock and create_stubs false unless their actual effects are needed and authorized.

Decisions

Make the deployment behavior explicit

Avoid these configuration mistakes

SituationCorrect decision
Flow exists but calls do not reach itVerify number routing, IVR binding, hours and telephony separately from flow creation
Web Messaging is configured but never opensCheck deployment activation, published configuration version, snippet and domain restrictions
SMS example uses buttonsProvide supported plain-text keyword/numeric input and test actual channel behavior
WhatsApp bot exists but inbound messages failVerify business integration/onboarding and Message Routing separately from bot YAML
A bot recognizes intent then disconnectsComplete the business action, return contract and handoff; recognition alone is not the service
YAML contains names without dependenciesUse resource/data-source backed substitutions or a justified explicit dependency
A Terraform update touches productionConfirm organization, region, backend and routed traffic before an authorized apply
Git code was reverted after an incidentRe-publish the known-good flow, restore mappings and test entry points; Git alone does not roll back the service

Validate at the right layer

Local syntax and schema checks are useful before deployment. Development-org checks establish that publishing, integrations and real channel paths work together. Production readiness additionally needs the correct destination, approved release scope, observed scenarios and a workable rollback. Do not substitute one layer's result for another.

Deployment effects matter

Applying genesyscloud_flow publishes the flow. A new version can immediately affect routed customer traffic. Saved Terraform plans can apply without another prompt. Flow publication, number purchase, account onboarding, campaigns and messages require their own authorized scope; generating documentation does not perform those actions.

Keep OAuth secrets and messaging tokens out of source and logs. Terraform state and plan files can contain sensitive values even when presentation is marked sensitive. Separate development and production state; a backend reconfiguration must not silently become a state migration.
