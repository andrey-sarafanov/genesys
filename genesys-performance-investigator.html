Using the skill

When to use it and what to provide

Use $genesys-performance-investigator for a scoped investigation of queue performance, IVR flow behavior or both.

It works as a consulting/reporting workflow: establish the selected entities and reporting clock, acquire daily and intraday evidence, explain the change and build a self-contained HTML report.

Useful inputs

  • Explicit queue and/or flow names or IDs. A flow-only investigation is valid.
  • Reporting question, date intent, media and a comparison period where relevant.
  • An authorized connector, supported portal access or exports with their filters and units.
  • Known operational changes and targets, when they are actual evidence rather than assumptions.

Example requests

Use $genesys-performance-investigator to compare Support and Billing since last Monday. Discover the reporting-view timezone, separate voice and messaging, and identify the 30-minute intervals driving the daily change.

Use $genesys-performance-investigator to investigate this IVR flow after its version change. Show daily executions and duration, keep outcome/version breakdowns separate, and explain what evidence is missing for a containment claim.

Use $genesys-performance-investigator to build an offline report from these aggregate response files and request metadata. Preserve missing statistics as unavailable and show the provisional current day.

How it differs from the reporting skill

Genesys Reporting covers general Analytics API selection, authentication and data pipelines. This skill specializes in a selected queue/flow investigation and its local report-building contract. CX as Code implements the flow or routing changes that might follow an investigation, when requested.

Helpers

Plan, collect and build the report

Prerequisites and separation of roles

Python 3.10 or newer and IANA timezone data are required. Windows may need a tzdata installation. The planner/builder uses the standard library and does not authenticate, call Genesys, acquire credentials or upload tenant data. The invoking agent collects data through an authorized connection.

Plan the requests

text
python <skill-dir>/scripts/genesys_report.py plan --timezone <discovered-IANA-zone> --queue-id <selected-id> --output <run-dir>/plan.json

Use repeated queue IDs for multiple selections; substitute or add --flow-id for flow work. Available options include --media, --flow-outcomes, --flow-versions, --start and an offset-aware --as-of. The output contains exact request candidates, not live performance results.

Acquire and preserve the evidence

Run the request through the actual authorized tool/API. Save raw responses and request metadata locally. Preserve daily, intraday, baseline, version and outcome slices as separate datasets. Record permission failures, gaps, freshness and availability explicitly.

Build the offline report

text
python <skill-dir>/scripts/genesys_report.py build --manifest <run-dir>/manifest.json --output <run-dir>/report.html

The manifest links scoped entities, request evidence, response files, timezone provenance, coverage and analyst-authored findings. The builder checks shapes, scope, overlap and statistics before computing display values.

Verify changed helpers

text
python <skill-dir>/scripts/test_genesys_report.py
node <skill-dir>/scripts/test_report_ui.mjs <synthetic-report.html>

Python checks cover aggregation, dates, scope, schema and escaping. The JavaScript checks use a minimal DOM stub and do not establish layout quality. A browser pass is still needed for filters, empty states, small-screen layout and runtime behavior.

Demonstrate without fabricating live evidence

A synthetic preview can be produced through the test helper's --demo-dir option and built from that directory's manifest. Keep demo:true so the persistent synthetic-data banner remains visible. Never use fixture rows to fill gaps in a live report.

Acquisition

Collect selected queue and flow evidence

Runtime tool schemas take precedence over these audited examples. Keep local per-run requests/responses immutable; record timestamps and never save credentials with evidence.

Discovery

  • list_queues(name_contains=...,page_size=100,page_number=1) returns queues,total,page_number,page_size. Paginate; match exact ID/division, not first substring.
  • Relevant GETs: /api/v2/routing/queues/{queueId} for selected settings; /api/v2/flows for paginated discovery; /api/v2/flows/{flowId} for metadata. Verify current API Explorer parameters/permissions before use.
  • mcp_health_check if exposed establishes server version/readiness, not every permission.
  • Portal: inspect Analytics Workspace timezone using supported browser UI without changing settings. A fixed offset alone does not identify a DST-aware IANA region. Record visible evidence, not browser storage.

Planner

Python 3.10+ with IANA zoneinfo data, no third-party dependencies:

bash
python3 <skill-dir>/scripts/genesys_report.py plan \
  --timezone '<discovered-IANA-zone>' --queue-id '<id-1>' --queue-id '<id-2>' --queue-id '<id-3>' \
  --output <run-dir>/plan.json

Use --flow-id instead of/alongside queues. Add --flow-outcomes and/or --flow-versions for separate breakdown datasets. Optional --start YYYY-MM-DD, --as-of <offset-aware-ISO-timestamp>, repeated --media voice. Defaults are last Monday through now, daily and PT30M. Plan does not execute requests.

Pass each requests[].request object to call_genesys_api: path,method,body. Save responses including envelope. Raw tool success is {"status":200,"data":{"results":[...]}}; queue wrapper has root results. Check transport and semantic errors.

Queues: POST /api/v2/analytics/conversations/aggregates/query, group queueId,mediaType, explicit nonempty queue OR filter AND media filter, plus interval,timeZone,granularity. Starter metrics retain counts, sums, SL and diagnostic components.

Flows: POST /api/v2/analytics/flows/aggregates/query, group flowId,mediaType, selected flow filter. Verified starter metrics are nFlow,tFlow,tFlowDisconnect,tFlowExit. Outcome option adds a separate dataset grouped by flowOutcomeId,flowOutcomeValue with nFlowOutcome,nFlowOutcomeFailed,tFlowOutcome; version option adds flowVersion. These match the official schema snapshot in api-contract.json. Recheck live schema on incompatibility; tenant instrumentation determines available values. Define outcome populations before deriving success rates; do not guess nFlowOutcomeSuccess. Extend exits/destinations/language in distinct slices if needed. In-queue flows may lack the requested outcome analytics.

Do not pass hypothetical fields or a flowId filter to the conversation aggregate endpoint without schema verification. The official query model accepting a string is not evidence the backend supports that metric.

Comparisons, detail and export fallback

Previous-week baselines need explicit matched local dates/hours and filters. Save baseline as a distinct slice; never include it in headline totals. Expanded direction/language/skill/wrap-up slices can multiply observations, so keep them separate from base queries.

For causal tests, fetch narrowly scoped conversation details through documented query/job endpoints. Follow pagination/cursors, record sampling/truncation and availability watermarks, and exclude customer details from HTML. Do not infer historical staffing from current snapshots.

Portal CSV must retain timezone, filters, units and denominators. Normalize to the documented aggregate envelope. If only averages/percentages were exported, leave missing sums/counts/numerators absent; pooled results remain N/A. Never manufacture sufficient statistics.

Start with two concurrent analytics queries. Respect 429 Retry-After; cap transient retries at three. Split size-limited queries into non-overlapping windows, preserving successes and explicit gaps. Poll existing async jobs after ambiguous timeouts. No unbounded organization-wide scans or credential refresh loops.

Analysis

Pool measures and test explanations

Durations in raw aggregates are milliseconds. Convert once to seconds. Missing is not zero; a zero denominator is N/A. Missing sufficient statistics invalidate a pooled measure rather than silently shrinking its population.

MeasureCalculation / interpretation
OfferednOffered.count; queue offers, not distinct callers
AnsweredtAnswered.count, not nConnected
AbandonedtAbandon.count; do not impose voice semantics on web messaging
HandledtHandle.count; differs from answered
ASAsum tAnswered.sum / sum tAnswered.count / 1000
AHTsum tHandle.sum / sum tHandle.count / 1000
Average wait/abandon timerespective tWait / tAbandon sum divided by its own count / 1000
Talk/hold/ACW averagesrespective tTalkComplete, tHeldComplete, tAcw sum / own count / 1000; different populations mean averages need not sum to AHT
Answer/abandon ratiorespective event count / offered; short-bucket event ratios are not same-cohort conversion rates
Service leveloServiceLevel; pool numerator/denominator, never average percentages. Ratio-only rows cannot establish pooled SL
Short abandonstShortAbandon.count when returned; source the configured threshold
TransfersnTransferred.count; document denominator for any rate
Flow volume/durationverified count metric (starter nFlow.count), and tFlow.sum / tFlow.count / 1000; executions, not unique customers
Outcomesretain ID/value; define eligible attempts before success rate. Multiple outcomes/versions/milestones are not additive total flow volume

Combine only disjoint rows with matching semantics, filters, granularity and timestamp convention. Never add daily and intraday queries. Selected-queue totals are workload, not deduplicated contacts: transfers/requeues and repeated flow visits count again. Do not invent a customer funnel by joining independent aggregates.

Callback aggregates are separate. Customer-first callback results may book on voice legs; callback offered/answered/abandoned/SL do not measure reach/bridge success. Use validated callback details and availability for outcomes. For message/email, use applicable metrics only. Missing abandon does not mean success. Queue metrics cannot establish agent occupancy, concurrency, productivity or historical staffing.

Investigation

  1. Check coverage, open interactions, provisional data, missing buckets, permissions and detail watermarks. Sparse results do not establish zero activity without verified omission semantics.
  2. Describe each entity/media separately. Show absolute volume change and percentage-point rate change; percentage change needs nonzero baseline.
  3. Find PT30M intervals driving daily differences. Compare like hours and operating calendars. Keep partial dates and DST offsets visible.
  4. Separate demand, effective capacity, handling workload, contact mix, transfers/routing and measurement changes. A weighted aggregate can worsen purely because mix changed.
  5. Test competing explanations with narrow additional evidence. A few days are descriptive variation, not established seasonality. Do not invent significance, control limits or business targets. SL configuration changes can invalidate comparisons.
Observed patternCandidate explanationNeeded evidence / alternative
Volume and delay riseDemand pressureSame-hour baseline and staffing; handling workload could also rise
Stable volume, delay worsensCapacity or routing reachHistorical routing statuses, staffing, eligibility and schedules; arrivals may have shifted within the day
AHT rise concentrated in ACWWorkflow changeWrap-up/contact mix and process history; complexity is an alternative
One queue grows, another shrinksRouting/transfer shiftFlow changes and linked transfer evidence; independent demand is possible
Flow disconnects rise, queue offers fallJourney/technical changeExit reason, outcome, flow version and technical evidence; successful self-service is also possible
Outcome success drops after new versionRegression or audience changeMatched version/intent cohorts and outcome instrumentation

Disconnect is not proof of containment. Self-service success requires an explicit business outcome, eligible population and any follow-up horizon. In their absence, report unavailable. Label findings with observation, hypothesis, confidence, alternatives, next test, owner and exact evidence references.

Report contract

Manifest, raw envelopes and coverage states

The helper requires Python 3.10+ and IANA timezone data; it uses only the standard library. It never connects to Genesys, handles credentials or uploads data. Acquisition is performed by the invoking agent through authorized tools. Keep each run in a dedicated directory.

plan emits exact request candidates. build accepts raw aggregate envelopes plus a manifest, validates scope/overlap, computes metrics and embeds normalized data into one HTML file. No server/CDN is required. It accepts camelCase API group IDs and the MCP's preserved group keys. Invalid shapes and error envelopes surface as unavailable data; unselected entities, overlapping buckets or malformed numeric statistics stop the build.

Example manifest (replace illustrative values with actual evidence; this is not live data):

json
{
  "title": "Selected queues: performance since Monday",
  "timezone": "Europe/London",
  "timezone_source": "Observed Analytics Workspace timezone selector, 2026-10-15T12:00:00Z",
  "interval": "2026-10-11T23:00:00Z/2026-10-15T12:00:00Z",
  "as_of": "2026-10-15T12:00:00Z",
  "entities": [{"kind":"queue","id":"user-selected-id","name":"User-selected queue"}],
  "datasets": [{
    "id":"queue-daily",
    "file":"queue-P1D.json",
    "kind":"queue",
    "granularity":"P1D",
    "slice":"base",
    "coverage":"provisional",
    "note":"Current day is incomplete; aggregate data may settle after extraction.",
    "request":{"method":"POST","path":"/api/v2/analytics/conversations/aggregates/query","body":{}}
  }],
  "limitations":["No matched historical baseline collected."],
  "findings":[]
}

Use the full actual request body, not the empty illustrative body above. datasets[].interval optionally narrows a dataset within the overall interval; comparison data outside that interval belongs in a separate manifest/report, or explicitly widen the report window and clearly name the separate baseline dataset. The UI never combines datasets.

Coverage values: complete, provisional, partial, unknown, unavailable. Label complete only after verifying requested coverage, limits and freshness; it does not certify a successful API response merely because HTTP returned 200. Overall current-day incompleteness and source freshness are distinct. Missing returned buckets are visibly flagged; sparse data is not zero-filled. If the API returns a bucket extending past the requested end, preserve the raw response and resolve its actual covered window; the builder rejects it rather than allocating a whole-bucket value to a partial interval.

Each dataset must contain only one non-overlapping time series per entity/media/additional group dimensions. Daily and intraday queries, alternative breakdowns, versions, outcome cohorts and baseline periods are separate datasets. If chunked responses contain overlapping boundary buckets, reconcile/refetch explicitly before build, not by silently dropping one.

Raw accepted shape:

json
{"results":[{"group":{"queueId":"user-selected-id","mediaType":"voice"},"data":[
 {"interval":"2026-10-11T23:00:00Z/2026-10-12T23:00:00Z","metrics":[
   {"metric":"nOffered","stats":{"count":100}},
   {"metric":"tAnswered","stats":{"count":90,"sum":1800000}},
   {"metric":"oServiceLevel","stats":{"numerator":75,"denominator":100}}
 ]}
]}]}

The raw API tool envelope {"status":200,"data":...} is also supported. Absence of a metric remains N/A. Callback answered/abandon/SL are excluded. Service-level ratio-only individual buckets can display; pooled SL remains N/A without numerators/denominators. Complete sufficient statistics are required across every contributing row. Qualified/duplicate metrics require an explicit semantic adapter; they are rejected rather than incorrectly combined.

Flow responses use flowId. Additional group keys (version, outcome ID/value, destination) remain separate. Any returned additional flow metric gets a generic count and, for time metrics, average-seconds selector. The agent must explain its verified business meaning and define outcome rates before adding calculated business measures; the renderer will not invent containment or success rates.

Findings format:

json
{
  "observation":"State an evidenced change with exact period and numbers.",
  "hypothesis":"State a plausible but unconfirmed mechanism.",
  "confidence":"low / medium / high, with rationale",
  "alternatives":["Alternative explanation"],
  "test":"Specific next evidence that could support or disprove the hypothesis.",
  "owner":"Suggested operational owner",
  "evidence":["queue-P1D.json, selected queue ID, local date, metric name"]
}

These entries are analyst-authored and remain scoped to their cited evidence when UI filters change. Missing findings produce an honest empty state.

For a reproducible synthetic preview, run scripts/test_genesys_report.py --demo-dir <temporary-directory>, then build that directory's manifest.json. Never use the fixture to populate a live report. The demo:true flag creates a persistent visible synthetic-data banner.

Run python3 scripts/test_genesys_report.py for aggregation, date, scope, schema and escaping checks. Optional JavaScript logic checks: node scripts/test_report_ui.mjs <synthetic-report.html>. This uses a minimal DOM stub, not a browser, and does not verify layout. During creation, 15 Python checks and these JS logic checks passed. Browser visual verification was blocked by the browser's local-file URL security policy; no alternate browser route was attempted. Live-tenant reconciliation has not been performed.

Acceptance scenarios

  • Three supplied queues: no other queue queried/rendered; pagination and duplicate names resolved.
  • Flow-only request: no queue requirement; per-day flow counts/duration and verified outcome/version breakdowns.
  • Missing selections: ask for them; do not run analytics against all entities.
  • Portal timezone unavailable or inconsistent: explain missing evidence and request clarification; no computer-timezone fallback.
  • Unequal queue volumes: pooled ASA/AHT/SL use sums and counts; incomplete stats yield N/A.
  • 403, empty response, missing metric, missing day, current partial day: visible distinct states; no fabricated zero or trend.
  • Sunday/Monday ambiguity, spring/fall DST and repeated-hour intraday data: explicit dates, offset-aware boundaries and no duplicate accumulation.
  • Callback/message rows: no invented voice-style abandonment or callback success.
  • Offline report: entity/media/dataset/metric filters, CSV export, printable view, readable small-screen layout, no external requests or runtime errors.
  • Adversarial display names: render as text, not HTML/script; CSV protects spreadsheet-formula prefixes.

Primary Genesys sources

  • Official API schema: successfully retrieved after the initial slow response. The compact api-contract.json preserves enumerated flow/conversation metric and grouping names, exact query permissions, retrieval date and full-source SHA-256. Starter and outcome/version request bodies are checked against it. Flow metrics include nFlow, nFlowOutcome, nFlowOutcomeFailed, tFlow, tFlowDisconnect, tFlowExit, tFlowOutcome; there is no nFlowOutcomeSuccess in this snapshot. Query permissions are analytics:flowAggregate:view and analytics:conversationAggregate:view, with analytics read scope; queue metadata requires routing:queue:view and flow metadata architect:flow:view. These are API permissions, distinct from the full portal-view permission set.
  • Official flow query model: verified timeZone, interval, granularity, groupBy and timestamp options. Its metric strings are not a catalogue of supported metrics; check live support before extending queries.
  • Official conversation query model: filtered queue query structure.
  • Flow query guide: research browser returned only a JS shell; not treated as readable evidence for detailed metric semantics.
  • Flows Performance Summary: reporting timezone selector, flow versions, destinations, division visibility and delayed speech/text metrics.
  • Flow Outcomes Summary: outcomes and permissions. Missing instrumentation is not a failed business outcome.
  • Performance columns: configuration-dependent SL denominator and event timing.
  • Reporting FAQs: offered, answered and handled can land in different intervals; web messaging does not share voice abandonment semantics.
  • Add a flow outcome: this feature excludes in-queue flow analytics.

An independent Gemini methodology critique was reviewed. Generic weighting and attribution cautions were useful; suggested metric names, a generic SL formula and overconfident causal language were rejected as technical evidence.

No tenant or live portal was accessed. Runtime permissions, tenant instrumentation, timezone and UI reconciliation remain live-run checks. Guidance concerns Genesys Cloud, not PureConnect or Engage. API behavior may change after this review.

Skill contract

The full skill instructions

Act as a Principal Genesys Cloud PS consultant and reporting analyst. Explain what changed, customer impact, plausible explanations, and the next evidence to collect. Never turn correlation into an established cause.

Establish scope and reporting time

  • The user selects queues and/or IVR flows. Ask for names or IDs when absent. “These three queues” without an actual selection is insufficient. Do not substitute busy queues or query the entire tenant. Support queue-only, flow-only, and combined reports; three is an example, not a limit.
  • Resolve names to IDs, divisions and flow types using connected tools or the signed-in Genesys Cloud portal. Paginate catalogues; resolve ambiguous names before querying. Preserve selected IDs and names.
  • Discover timezone from Genesys Cloud before asking the user. Use supported browser tools to read the timezone in Analytics Workspace / the relevant performance view; record location and observed value as timezone_source. This is a reporting-view setting, not proof of one universal tenant timezone. Cross-check business-unit or operating-schedule settings when relevant. Never infer timezone from API region, computer timezone or user location. If inaccessible, ambiguous or conflicting, ask the user to resolve it. Do not guess an IANA region from a UTC offset.
  • Resolve “since last Monday” to explicit dates in that IANA timezone. Default to the most recent Monday strictly before today (on Monday, seven days earlier); state the interpretation. On Thursday 2026-10-15 this means Monday 2026-10-12. End at one frozen extraction timestamp; mark today partial. Use local calendar midnights, half-open intervals and DST-aware conversion. Compare partial days only with equivalent elapsed windows, or exclude them from deltas.
  • Read research.md for the audited findings, collection.md for acquisition contracts and analysis.md before interpretation.

Acquire evidence

Discover available tool schemas; do not assume an MCP prefix or installed version. Prefer an existing authorized Genesys connector. The researched server is optional: this skill also accepts official Platform API aggregate responses or correctly mapped portal exports. Do not run the upstream installer merely to use this skill.

Reporting authorizes relevant GETs and documented analytics query/job POSTs, not tenant changes. The upstream generic API tool accepts write methods: do not use PUT, PATCH, DELETE or operational POSTs. Do not read credential stores, browser state, local session histories or token files. Use existing authenticated connectors or supported browser UI. Keep tenant data local; do not send it to delegate models or external sites.

  1. Record tool/version, selections, timezone provenance, media filters, readable queue SL configuration, date window and extraction time.
  2. Generate explicit bodies with scripts/genesys_report.py plan. Collect daily and PT30M data for the same scope; collect separate comparison windows if needed. Keep request and response files locally. The helper makes no network calls.
  3. Use call_genesys_api with generated method/path/body, or an equivalent official connector. queue_performance(mode="full") works where its contract fits, but the audited version lacks a timezone parameter. Prefer raw timeZone queries for calendar slicing. Never use empty queue filters.
  4. Flows require separate flow aggregates, with outcome and destination/version slices when supported and useful. Queue metrics cannot substitute for IVR metrics. Verify live metric/dimension support before extending starter queries.
  5. Preserve permission failures, truncation, missing data and availability watermarks. A successful job does not prove completeness. Stop repeated permission failures; respect Retry-After and bound transient retries. Inspect an existing async job after a timeout instead of submitting it repeatedly.
  6. Without live access, identify the missing connection or required exports. Never invent tenant results. Synthetic data is for tests only and must remain prominently labelled.

Analyse and explain

Use sufficient statistics, not averages of averages; see analysis.md. The builder handles weighted results, unknowns, callback exclusions, separate media, generic flow measures and source hashes. It does not infer causes, deduplicate callers or reconstruct absent denominators.

Inspect daily differences and contributing PT30M intervals. Separate volume and rate changes, media/intent mix, routing and flow versions. Add like-for-like previous-week comparisons when justified, with calendar and partial-period caveats. A few days do not establish seasonality. Missing historical baseline means no baseline conclusion.

Write findings as observation, hypothesis, confidence, alternatives, test, owner, and evidence (file + bucket/metric). Explain why metrics matter. Rank next actions by customer impact and evidence strength. Confidence describes the hypothesis, not certainty that a dashboard number is causal. Do not diagnose individual agents from queue aggregates.

Understand what the report can establish

Common investigation mistakes

  • Inferring reporting timezone from API region or computer settings.
  • Querying all queues because the user omitted an explicit selection.
  • Averaging queue percentages or duration averages without weights.
  • Adding daily and intraday observations or overlapping outcome/version datasets.
  • Treating no returned bucket, a missing metric and confirmed zero as equivalent.
  • Using queue aggregates to diagnose an individual agent or infer historical staffing.
  • Claiming successful self-service from a disconnect or absent failed-outcome metric.

Evidence that closes a hypothesis

Describe the observation first, including exact interval and metric. State a plausible mechanism, alternatives and why confidence has that level. Specify a narrow test, suggested owner and exact evidence reference. If a comparison baseline or historical configuration is unavailable, preserve that limitation in the report.

Live acceptance

Reconcile one queue-day-media slice with identical portal filters and timezone. Compare additive daily and intraday totals over the same covered instants. Open the generated report and exercise its controls. Local fixture checks and prior skill-authoring results are not a new live-tenant reconciliation.
